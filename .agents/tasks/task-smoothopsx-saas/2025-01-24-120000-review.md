# SmoothOpsX: Full-stack regulatory compliance changelog platform

A complete SaaS application replacing a previous Node.js worker (`index.js`, `Procfile`) with a Next.js 14 App Router application. The platform presents a landing page, credential-based auth, a 3-step onboarding wizard, a filterable compliance feed, regulation detail pages with action items, and email alert preference settings. Data layer is PostgreSQL via Prisma, with 14 seeded regulations and 45 action items. Authentication uses NextAuth.js with the credentials provider and JWT session strategy.

**Watch for:** Action items have no ownership check — any authenticated user can update any other user's action status (confirmed). Region strings in onboarding don't match seed data, making the filtered feed return zero results for all users (confirmed). All client-side data fetches swallow errors silently, giving users no feedback on failures (confirmed).

## High-level view

The auth layer uses bcrypt + JWT via NextAuth's credentials provider. Route protection lives in middleware that redirects unauthenticated users away from `/dashboard` and `/onboarding`. The `NEXTAUTH_SECRET` ships as a placeholder in `.env` — acceptable for development but there's no guard against deploying with it. No rate limiting exists on auth endpoints.

The data model separates global regulations from per-user action tracking via a `UserActionItem` join table. The regulations API respects user region preferences and supports search, severity, category, and date-range filters. However, the action item PATCH endpoint verifies the action item exists but never checks whether the calling user has a relationship to that item's regulation — it trusts the caller's intent.

The onboarding flow collects business type, tech stack, and regions through a multi-step wizard but performs no server-side validation beyond checking that values are present and that arrays are arrays. Critically, the region values presented in onboarding (`"EU - GDPR"`, `"US - California/CCPA"`) don't match the values in seed data (`"EU"`, `"US"`, `"Global"`), making the entire filtering pipeline non-functional.

Frontend pages are entirely client-rendered (`"use client"` throughout the dashboard). Every API call uses empty `catch` blocks that discard error information, so users see loading states resolve to empty results without explanation when requests fail. The user's tech stack selection is stored during onboarding but never used for filtering anywhere.

There are no tests of any kind in this changeset.

## Authorization gap on action item updates

The PATCH handler at `app/api/actions/[id]/route.ts` verifies the session contains a user ID and that the action item exists, then performs an upsert on `UserActionItem`. It never checks whether the action item belongs to a regulation in the user's region or whether the user should have access to that item at all. The upsert creates a `UserActionItem` record regardless, meaning users can "complete" action items from regulations they shouldn't see.

```typescript
// Current check: only verifies existence
const actionItem = await prisma.actionItem.findUnique({
  where: { id: params.id },
});
if (!actionItem) {
  return NextResponse.json({ error: "Action item not found" }, { status: 404 });
}
// Missing: verify actionItem.regulation.region is in user.regions
```

This is a horizontal privilege escalation vector. The impact is limited (users can only mark items for themselves, not for others) but it bypasses the region-based scoping that the rest of the app enforces.

## Region value mismatch between onboarding and seed data

The onboarding page defines regions as `"EU - GDPR"`, `"US - California/CCPA"`, `"US - Federal"`, `"United Kingdom"`, etc. The seed data uses `"EU"`, `"US"`, `"Global"`, `"UK"`, `"Brazil"`, `"Singapore"`, `"Australia"`. The regulations API filters by `where.region = { in: user.regions }`. Since `"EU - GDPR" !== "EU"`, a user who completes onboarding with the available options will receive zero matching regulations. The feature is functionally broken as shipped.

This is the highest-severity bug in the changeset because it renders the core product experience non-functional for any user who goes through the intended flow.

## Onboarding input validation

The onboarding API at `app/api/onboarding/route.ts` checks only structural shape:

```typescript
if (!businessType || !Array.isArray(techStack) || !Array.isArray(regions)) {
  return NextResponse.json({ error: "Invalid input" }, { status: 400 });
}
```

A client can POST `{ "businessType": "anything", "techStack": ["arbitrary"], "regions": ["nonsense"] }` and it goes straight into the database. These fields drive filtering logic, so garbage values silently break the feed for that user. Server-side validation against the same allowed-value sets used in the frontend would close this gap.

## Silent error handling across the dashboard

Every client page follows this pattern:

```typescript
} catch {
  // fetch failed
}
```

When the API returns a 500 or the network drops, the user sees either an empty list or a stale loading state. There's no error boundary, no retry mechanism, and no user-facing notification. For a compliance platform where missing data means missed deadlines, silent failures are a product risk.

## Authentication and session security

The `.env` file is committed with `NEXTAUTH_SECRET="dummy-secret-for-build"`. The `.gitignore` excludes `.env` (correctly), but the file is already tracked — it was added in this diff. Anyone with repo access can see the placeholder, and if it's used in production, JWT tokens are forgeable with a known secret.

There's no rate limiting on `/api/auth/register` or the NextAuth sign-in endpoint. A determined attacker can brute-force credentials or mass-create accounts without throttling.

Email verification is modeled in the schema (`emailVerified` field) but never implemented. Users can register with any email address and immediately access the full platform.

## Unused tech stack filtering

`techStack` on the User model and `techStackRelevance` on ActionItem are both stored but never connected. The regulations feed filters by region but not by tech stack. The actions endpoint similarly ignores tech stack relevance. The onboarding wizard collects this data and the schema models it, but nothing in the query layer uses it. This is either dead data or an incomplete feature.

## No test coverage

Zero test files, no testing libraries in dependencies. The authorization gap, the region mismatch, and the validation holes all shipped without automated verification. The seed script provides realistic data but isn't a substitute for tests.
